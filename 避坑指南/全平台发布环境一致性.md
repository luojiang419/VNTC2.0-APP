# 全平台发布环境一致性

## ziglang wheel 安装成功不等于 zig 命令可用

表现：Ubuntu Runner 上 pip 安装 ziglang 0.13.0 成功，但紧接着 `zig version` 返回 command not found。

根因：该 wheel 把原生 zig 放在 Python 模块目录，没有在 Runner PATH 中提供同名入口。cargo-zigbuild 还需要 Python 用户 bin 被纳入 PATH。

解决：通过 `python3 -c 'import pathlib, ziglang; print(pathlib.Path(ziglang.__file__).parent)'` 取得实际目录，当前步骤导出 PATH，并将其和 `$HOME/.local/bin` 写入 `$GITHUB_PATH` 供后续步骤使用。不要只安装成功就开始交叉构建。

验证：工作流 actionlint 检查通过；各架构发布 job 必须先执行 `zig version`、`cargo zigbuild --help`，再编译真实静态 ELF 并执行对应 QEMU `--help`。

## Flutter SDK 版本必须与严格锁文件一致

表现：本地 Flutter 3.41.7 测试通过，CI 固定 Flutter 3.44.2 的 `pub get --enforce-lockfile` 失败，提示 meta、test、test_api、test_core 四项需要变化。

根因：Flutter SDK 自身固定了一组测试依赖。旧 SDK 重新生成的锁文件会覆盖新 SDK 所需版本，业务依赖没有改变也会失败。

解决：用隔离的、与 CI 相同的 Flutter 3.44.2 SDK 执行普通 pub get，检查只更新必要依赖，然后执行 `pub get --enforce-lockfile`、静态分析和测试。不要关闭严格检查，也不要为解决锁文件而升级所有依赖。后续本地发布检查应继续使用匹配 SDK，避免旧 SDK 再次改写锁文件。

验证：四项依赖按 SDK 要求更新；同版本严格解析通过，静态分析 0 问题。云端最终构建状态与 Release 下载验收以 `全平台发布任务.md` 为准。

## musl 构建成功仍要执行产物

表现：Rust 1.88 在 Ubuntu 22.04/musl 1.2.2 的 musl-gcc 环境成功生成 x86_64 release，但执行 `--help` 即 SIGSEGV；相同源码 ARM Zig 构建启动正常。

定位与解决：本地 Ubuntu 24.04/musl 1.2.4、同一 Rust 1.88 完整重编后，真实启动和 29 项测试通过。将 x86_64 CI Runner 对齐到这个已验证环境，ARM 保留已通过镜像；缓存 key 包含镜像，保留构建后启动检查。证据指向 musl 链接环境差异，未进一步将其归因于某个上游补丁。不要移除启动检查，也不要把编译成功当作程序可运行。

## Android SDK 废弃 tools 包

表现：setup-android v3.2.2 运行 `sdkmanager tools`，出现 `Failed to find package 'tools'`，原生库尚未开始编译即退出。

根因：该 action 固定提交的默认 packages 为 `tools platform-tools`，上游 SDK 仓库已不再提供旧 tools 包。

解决：两处 setup-android 显式设置 `packages: platform-tools`，继续由后续步骤安装项目固定的 NDK 和 build-tools。不能把这个工具准备故障当作原生代码或 APK 构建失败。action.yml 默认值已通过 API 核对，工作流静态检查通过；云端验证结果见发布任务文档。
