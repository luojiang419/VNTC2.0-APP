# OpenWrt 网关转发与仿真验收

## VNT 输入路由不等于 Linux 内核路由

表现：虚拟 IP 互通，但去往远端 LAN 的流量仍走默认出口。根因：VNT Core 的 input 只决定进入 TUN 后选择哪个远端节点，当前 NetworkManager 只配置 TUN IP，没有安装目标网段系统路由。

解决：OpenWrt 客户端连接后按 input 创建内核路由；用连接生命周期的 guard 清理，不使用 route replace，已有路由冲突时明确报错。默认路由与虚拟网段覆盖必须拒绝。验证需使用独立 LAN 终端，不能只在路由器上 ping 自身虚拟接口。

## fw4 check 成功仍可能跳过无效规则

实测 firewall4 的 NAT 节 dest_ip 不接受 list；输出 `option 'dest_ip' must not be a list` 和 `skipped due to invalid options`，但 check/reload 仍返回成功。

解决：每个 NAT 目标网段生成一个独立节；除退出码外检查本插件节的 skipped/invalid 警告，失败恢复原防火墙文件。最终通过实际跨 LAN 流量验证，不能只凭 UCI 内容或命令返回码判断生效。

## UCI -c 不隔离暂存修改

表现：无效配置被拒绝后，正式防火墙文件哈希不变，但 `uci changes firewall` 出现残留，下一次操作被暂存保护阻止。根因：`uci -c` 只改变配置目录，保存修改的 savedir 仍默认指向全局 /tmp/.uci。

解决：构建候选配置时同时指定 `-c 临时配置目录 -t 临时delta目录`；在无效配置、规则占用冲突和重复应用后检查正式文件及全局暂存区均未变化。不能在生产脚本中用无条件 `uci revert firewall` 清理，因为那会丢弃用户修改。

## OpenWrt functions.sh 不兼容全局 nounset

直接 set -u 后加载 /lib/functions.sh，会因可选的 IPKG_INSTROOT 未定义退出，导致 procd 客户端未启动。调用该库的 helper 使用 set -e，并对实际配置显式校验；不要将安装命令返回 0 等同于客户端已运行。

## LAN 到较小 MTU 的 TUN

LAN 常为 1500，VNT 默认为 1400。网关专用分区使用 fw4 mtu_fix，使两方向 TCP SYN 调整 MSS；同时保留 ICMP 以允许 PMTU。验证应检查生成的 mangle_forward 规则和实际大文件、视频、UDP 通路。

## 软件仿真的负载边界

单 vCPU TCG 需要同时仿真两次内核转发、conntrack/NAT 和加密中继。首轮无节制大文件与多路视频/UDP 叠加曾出现 guest CPU 满载、10% 大包未及时收到及约 14 秒 RTT，不能记录为通过，也不能推导物理路由器的带宽。

功能验收应声明文件源限速、视频并发和数据报频率，完整记录实际持续时间、SHA-256、RTP 序号和丢包；超载记录保留。最大吞吐和拥塞下的服务质量需要另做性能验收。

## x86 嵌套 TCG 复位与 SSH 就绪

本机 QEMU 8.2.2 的 x86 复位曾在内核解压、清理旧代码页时进展极慢，监控反复停在 REP 写入并出现 RCU stall。增大内存、关闭随机化、改用 kexec 都没有单独解决。最终验证通过的组合是官方原始内核 ELF/PVH、max CPU、512MiB、单线程 TCG、8MiB 翻译缓存与可靠 TSC；详细命令见 provision_x86_gateway.py。先前失败和恢复日志保留，恢复 QEMU 进程的冷启动不计作热重启。

SSH 连接成功不代表新内核已启动，旧系统退出过程仍可能接受连接；需要轮询 boot_id 变化并确认 QEMU PID 不变，再验证 VNT 和数据面。Paramiko 的 channel.exec_command 在等待请求 ACK 时不受普通读取超时控制，重启边界可能永久等待；验证器用独立线程截止时间关闭超时通道，防止检测脚本挂住。普通数据传输仍逐次校验，不用重试掩盖内容错误。
